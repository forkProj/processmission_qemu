QEMU TCG 插件
=============


编写插件
--------

API 版本
~~~~~~~~

插件是 QEMU 的新功能，允许开发树外插件并动态链接到运行中的 QEMU。
但项目保留按需修改或破坏 API 的权利。
避免兼容问题的最好方式是将插件提交上游，以便 API 改变时一起更新。

所有插件必须导出声明构建时 API 版本的符号，例如::

  QEMU_PLUGIN_EXPORT int qemu_plugin_version = QEMU_PLUGIN_VERSION;

未导出 qemu_plugin_version，或版本超出 QEMU 支持范围时，核心拒绝加载。

传给 qemu_plugin_install 的 qemu_info_t 还会给出最低和当前支持版本。
添加 API 时递增当前版本，修改或移除已有 API 时递增最低版本。

查询句柄生命周期
~~~~~~~~~~~~~~~~

每个回调提供不透明信息句柄，通常可继续查询翻译、指令或操作的信息。
句柄只在回调期间有效，因此需要的信息必须在回调中提取并由插件保存。

插件生命周期
~~~~~~~~~~~~

首先加载插件并调用公开的 qemu_plugin_install，再由插件注册各类事件回调。
希望程序或系统结束时输出统计摘要的插件，通常注册 atexit 处理器。

事件发生时调用回调，可能提供额外信息。
翻译事件允许枚举块内指令，并为部分或全部指令注册执行回调。

也可以添加执行加法、存储立即数等操作的内联指令，
或根据内联计算的条件决定是否执行回调。
这些操作关联 scoreboard，它是随核心或线程创建自动扩容的线程本地存储，
无需加锁即可安全访问和修改。
内联操作与条件回调结合，比传统回调更高效地插桩二进制程序。

QEMU 退出时调用全部已注册 atexit 回调。

QEMU 内部细节的暴露
~~~~~~~~~~~~~~~~~~~

插件架构刻意避免暴露翻译实现细节。
虽然存在翻译时刻、翻译块等概念，其内部对插件仍不透明。
只能通过导出的 qemu_plugin 函数查询指定指令细节和系统配置。

不过可以依赖以下假设。

翻译块
++++++++

全部代码都经过翻译，但翻译结果不一定执行。
要知道实际发生什么，必须对执行本身插桩。

同一地址被多次翻译很正常。
跟踪系统模式代码时，应查看 qemu_plugin_insn_haddr 提供的底层物理地址，
考虑虚拟内存影响；若系统发生换页，物理地址也可能变化。

块内不一定执行所有指令，要准确跟踪单条指令必须直接插桩。
不过异步中断不会在块中途改变控制流。

指令
++++++++

指令插桩在执行前运行，能确定指令即将分派，却不能确定一定完成。
通常是因为执行触发 SIGILL 等同步异常。
若需确认完成，还应插桩下一指令。
execlog.c 展示如何跟踪并在执行后补齐信息。

内存访问
++++++++

内存回调在加载或存储成功后调用。
失败访问对内存插桩不可见，但可观察其执行副作用，例如进入异常处理器。

系统空闲和恢复状态
++++++++++++++++++

qemu_plugin_register_vcpu_idle_cb 和 qemu_plugin_register_vcpu_resume_cb
可跟踪 CPU 等待外部 I/O 时进入和退出睡眠。
模拟效率较低，使 CPU 空闲机会更少，因此事件频率可能低于真实硬件。

内部实现
--------

加锁
~~~~~~~~

必须避免死锁，尤其在 MTTCG 下。
从插件代码调用时会加锁，回调列表同时受 RCU 保护，
因此执行回调无需持锁。
这也有利于性能，因为内存访问等回调可能非常频繁。

  * 因此维护自己的 CPU 列表，避免与 cpu_list_lock 的加锁顺序问题。
  * 使用递归锁，因为回调中可能再次注册。

注册和注销因加锁而较慢，但很少发生。
重点是调用或跳过回调时的性能，而非注册性能，RCU 很适合这一需求。

插件可随时请求卸载，包括在回调中，适合不再需要插桩时自行移除。
卸载是异步的，请求后仍可能触发回调。
只有全部 vCPU 静止时的安全工作执行完成，才算完全卸载。
